# Research: Industry DSLs & Specs for Expressing Business Logic Declaratively

*(Informing a business-logic layer for ElastiCORE — currently entity/DTO/enum/port declarative YAML with DDD annotations `@root/@aggregate/@invariant/@event/@factory/@specification`)*

## 1. Workflow / Process

- **BPMN 2.0** (OMG standard, XML-based graphical+executable notation) + **DMN** (decision tables, FEEL expressions) — implemented by **Camunda 8 / Zeebe** (stable 8.8, Oct 2025). Grammar: XML graph of `<process>`, `<sequenceFlow>`, gateways, events; DMN adds decision tables. Expresses control flow, gateways, sub-processes, boundary events, compensation, timers extremely well; poor fit for arbitrary data transformation (escape hatch: service tasks calling Java/JS delegates, or FEEL/JUEL expressions in gateway conditions). Zeebe is horizontally scalable, no central DB, gRPC headless API. Criticism: BPMN 2.0 is "over-engineered," unclear to business analysts, developers *and* managers alike; the jump from descriptive to executable level adds real complexity ("BPMN 2.0: no longer for Business Professionals"). Adoption: dominant in enterprise BPM (many vendors, Wikipedia lists 20+ engines). ([Camunda BPMN](https://camunda.com/bpmn/), [Zeebe overview](https://docs.camunda.io/docs/components/zeebe/zeebe-overview/), [BPMN criticism](https://social-biz.org/2010/09/01/bpmn-2-0-no-longer-for-business-professionals/), [struggle with BPMN](https://www.researchgate.net/publication/27478001_Opportunities_and_constraints_The_current_struggle_with_BPMN))
- **CNCF Serverless Workflow** — now at **1.0.x** (a rewrite, "Open Workflow DSL"), JSON/YAML, unifies former "states" into a single `task` concept, removing nesting limits. Supports HTTP/gRPC/OpenAPI/AsyncAPI calls, event-driven execution, retries/timeouts, and **saga/compensation via try-catch blocks with reverse-order compensating steps** — directly comparable to a `port:` escape-hatch model. Escape hatch: custom function tasks (script/shell/container). Governance: CNCF sandbox project, versioned spec + JSON Schema, conformance via reference SDKs (Java/Go). ([spec site](https://serverlessworkflow.io/), [1.0 release notes](https://serverlessworkflow.io/blog/releases/release-100/), [saga pattern](https://kiegroup.github.io/kogito-docs/serverlessworkflow/1.36.1.Final/use-cases/orchestration-based-saga-pattern.html))
- **AWS States Language (ASL)** — JSON, spec version "1.0" fixed since inception, at states-language.net. Grammar: `States` map of typed nodes (`Task`, `Choice`, `Parallel`, `Map`, `Wait`, `Pass`, `Fail`, `Succeed`), `Next`/`End`, `Retry`/`Catch` blocks. No native compensation — sagas must be hand-modeled with explicit catch branches. Escape hatch: `Task` invokes Lambda/any AWS service (Resource ARN) — logic always lives outside the DSL. Extremely stable, heavily adopted (Step Functions is core AWS orchestration). ([spec](https://states-language.net/), [AWS docs](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-amazon-states-language.html))
- **Temporal** is explicitly **code-first**, not declarative — workflows are real functions (Go/Java/TS/Python) executed deterministically and replayed from an event history. This is the strongest counter-example in the survey: Temporal's authors argue any declarative DSL is a "subset of what code can express," so they went the other way. Costs: steep learning curve (~1 month to productivity), determinism/versioning constraints on workflow code, harder cross-team review than YAML. ([Temporal alternatives comparison](https://kestra.io/resources/infrastructure/temporal-alternatives), [workflow definition docs](https://docs.temporal.io/workflow-definition))
- **Argo Workflows**: Kubernetes CRDs (YAML), DAG/steps templates, container-native — good code-gen target if ElastiCORE ever needs k8s-level orchestration, but logic per step is opaque (container image). **Netflix Conductor**: JSON blueprints, language-agnostic task workers — closest in spirit to a "declare the graph, execute via workers" model. **Kestra**: declarative YAML unifying data/AI/infra/business flows, with a plugin ecosystem including AI tasks. **Azure Logic Apps**: JSON workflow definition + visual designer + managed connectors, code-optional. **Zeebe**: see BPMN above. ([comparison](https://kestra.io/resources/infrastructure/orkes-conductor-alternatives), [Argo alternatives](https://kestra.io/resources/infrastructure/argo-workflows-alternatives))

## 2. Rules / Decisions

- **Drools DRL**: free-form `.drl` rule files, forward/backward-chaining (Rete) inference engine; also supports DMN natively. Expresses complex multi-fact pattern matching well; poor fit for simple per-field validation (heavyweight). Escape hatch: RHS ("then") blocks are raw Java. ([Drools DMN docs](https://docs.drools.org/latest/drools-docs/drools/DMN/index.html))
- **DMN + FEEL**: decision tables + a friendly expression language (FEEL) standardized by OMG, conformance levels 1–3 (level 3 = full boxed expressions + fully executable). Strong fit for tabular business rules (discount tiers, eligibility); weak for imperative control flow. ([Drools DMN](https://docs.drools.org/latest/drools-docs/drools/DMN/index.html))
- **OPA / Rego**: declarative logic-programming language for policy-as-code, dominant in Kubernetes admission control (sub-millisecond eval, deep k8s integration). **Real, widely-reported criticism**: steep learning curve, SQL-like/Prolog-like unification model unintuitive to imperative programmers and to non-engineer compliance staff; policy sets become hard to maintain at scale. ([intro](https://dev.to/spacelift/introduction-to-open-policy-agent-opa-rego-language-5cmg), [criticism](https://www.techtarget.com/it-infrastructure/news/252467102/Kubernetes-policy-project-takes-enterprise-IT-by-storm))
- **Cedar** (AWS, open-sourced May 2023): purpose-built PARC(context) authorization language, RBAC+ABAC, used by Amazon Verified Permissions. Distinguishing feature: AWS **formally verifies** the engine (Lean/automated reasoning proofs of safety/correctness matched against the Rust implementation) — a strong verification story ElastiCORE could cite as a target bar. ([AWS Cedar intro](https://aws.amazon.com/about-aws/whats-new/2023/05/cedar-open-source-language-access-control), [AVP docs](https://docs.aws.amazon.com/verifiedpermissions/))
- **JSON Logic**: minimal Lisp-like JSON rule format, no `eval`, no loops/setters/gotos, deterministic and side-effect-free by construction — the safety model closest to what a code-gen DSL needs for embedded "field-level" predicates. Community-maintained spec at jsonlogic.com; multiple Java ports (`json-logic-java`). ([site](https://jsonlogic.com/), [safety](https://endjin.com/blog/introducing-corvus-text-json-v5-jsonlogic))
- **Google CEL**: expression language, non-Turing-complete, evaluates in **linear time, is mutation-free, and provably terminating** — explicitly designed so embedding apps can safely run untrusted expressions fast. Used in **Kubernetes** (`x-kubernetes-validations`, admission policies, evaluated in-process in the API server) and originated from **Firebase Rules**. `cel-java` and other language bindings exist; spec lives at `google/cel-spec` (now mirrored under `cel-expr/cel-spec`) and cel.dev. This is the standout candidate for ElastiCORE's expression needs given the Java/Spring target. ([cel-spec](https://github.com/google/cel-spec), [cel.dev](https://cel.dev/), [k8s CEL](https://kubernetes.io/docs/reference/using-api/cel/))

## 3. State Machines

- **SCXML**: W3C Recommendation (2015) for event-based state machine notation, unifying Harel statecharts + CCXML concepts; XML interchange format, multiple interpreters (uscxml, C/C++/Java/Python/Lua bindings). ([W3C spec](https://www.w3.org/TR/scxml/))
- **XState**: JSON/TS statechart definitions modeled closely on SCXML semantics, executed by a JS/TS runtime; **Stately** provides a visual editor/hosted service on top. Good precedent for "declare the machine as data, execute with a small deterministic interpreter."
- **Spring Statemachine**: Java DSL/builder (not YAML) for state machines directly in the Spring ecosystem ElastiCORE already targets — worth studying its transition/guard/action API shape even though it's code, not declarative YAML.
- **AWS Step Functions** doubles as a state-machine spec (see §1).

## 4. Data/DDL DSLs That Added Logic Later

- **JHipster JDL**: single-file DSL for entities/relationships/deployments; deliberately **does not** try to express business logic — it generates a `service` layer stub (`with serviceClass`) and leaves logic to hand-written Java, i.e. JDL's authors chose the same boundary ElastiCORE has (declare structure, generate a seam, write logic in code). ([JDL intro](https://www.jhipster.tech/jdl/intro/))
- **Hasura**: permissions are declarative (role-based row/column rules); **Actions** are the explicit "custom business logic" escape hatch (webhook to your own service, contract defined by GraphQL schema); **Event Triggers** give async reactive logic on INSERT/UPDATE/DELETE. This three-tier split (declarative permissions / typed action contracts / event triggers) is a clean analog for ElastiCORE's `port:` block. ([Actions](https://hasura.io/blog/introducing-actions), [event triggers](https://hasura.io/docs/2.0/event-triggers/overview/))
- **Prisma + Zod**: Prisma schema is pure DDL; **Zod schemas are generated from it** to add runtime validation logic — i.e., logic-generation is a downstream code-gen step off the same schema, not embedded in the schema DSL itself. ([Prisma→Zod](https://www.lambdaworks.io/blog/from-prisma-to-zod))
- **Supabase RLS**: business rules expressed as literal SQL `CREATE POLICY ... USING (...) WITH CHECK (...)` clauses attached to tables — declarative but the expression language is full SQL, not a restricted grammar, and it lives in the database, not the ORM/DSL layer. ([RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security))
- **Mendix/OutSystems**: microflows/server actions are **visual graphs of typed steps** (validation, calculation, API call, email) with an explicit code-escape (Java actions in Mendix, C#/.NET "Extensions" in OutSystems) — validates that low-code vendors converge on "graph of typed nodes + named escape hatch to real code," the same pattern as BPMN/ASL. ([comparison](https://www.superblocks.com/blog/mendix-vs-outsystems))
- **Salesforce Flow vs Apex**: canonical "declarative-first, code-when-complex" boundary. Explicit hybrid pattern: invocable Apex methods callable from Flow, and their guidance literally states "Flow for simple/repetitive, Apex for intricate/transactional/high-volume" — a clean articulation ElastiCORE's guide docs could borrow verbatim. ([guide](https://medium.com/@akash15_dev/salesforce-flow-vs-apex-when-to-use-what-complete-guide-for-2025-5ccf12735a8f))
- **Sylius/Shopware**: business-process state (order/payment/shipping) modeled via **Symfony Workflow Component** (or legacy Winzou State Machine) as YAML config of places/transitions/guards, with PHP event listeners as the escape hatch for side effects — another declarative-state + code-callback split. ([Sylius state machine](https://docs.sylius.com/the-book/architecture/state-machine))
- **Ballerina**: a full general-purpose language, but with declarative, type-safe network/service constructs baked into syntax (not a DSL layered on top) — less directly transferable.
- **Jolie**: microservice orchestration language mixing imperative constructs with first-class "port"/communication primitives — notably, Jolie's own vocabulary literally calls its I/O declarations "ports," which is a naming precedent ElastiCORE already independently arrived at.
- **Encore.dev / Wing / Nitric**: "infrastructure-from-code" — infra (DBs, queues, cron, APIs) declared via annotations/keywords directly in TS/Go/Wing source, compiled to Terraform/CloudFormation + runtime code. This is the *opposite* direction from ElastiCORE (code declares infra, rather than YAML generating code), useful as a contrast case. ([Encore](https://encore.dev/introduction), [Wing](https://www.winglang.io/))
- **Convex**: queries/mutations/actions are plain TypeScript functions over a reactive DB with automatic transactionality — logic is 100% code, but schema/reactivity is declarative; shows a system that deliberately did *not* build a rules DSL for its logic layer.
- **Dark lang**: cautionary tale — Dark Inc. shut down in 2024/25 ("Winding Down Darklang-Classic"), the "always-deployed" structured-editor language pivoted to a new functional-language project under a new company; a useful adoption-risk data point for any bespoke DSL bet. ([status](https://blog.darklang.com/winding-down-darklang-classic/))

## 5. Event / DDD Tooling

- **Context Mapper DSL (CML)**: Xtext-based, the most directly relevant precedent. Grammar formalizes **strategic** DDD (Bounded Context, Context Map, Supplier/Customer relationships, exposed Aggregates) and, via an integrated Sculptor sub-DSL, **tactical** DDD (Entity, Aggregate, Value Object, Domain Event, Service, Repository) — i.e., almost exactly ElastiCORE's `@root/@aggregate/@invariant/@event/@factory/@specification` set, but with a grammar spec (`.xtext` file) and model-transformation pipeline (generates PlantUML, MDSL service contracts, or code) that ElastiCORE lacks. Worth pulling the actual `.xtext` grammar file for aggregate/service/flow rules. ([grammar file](https://github.com/ContextMapper/context-mapper-dsl/blob/master/org.contextmapper.dsl/src/org/contextmapper/dsl/ContextMappingDSL.xtext), [aggregate docs](https://contextmapper.org/docs/aggregate/), [tactic DDD](https://contextmapper.org/docs/tactic-ddd/))
- **Axon Framework**: sagas are aggregates with event-driven listeners; invocation/compensation are separate event handlers — code-first, annotation-driven (`@Saga`, `@SagaEventHandler`), not YAML.
- **MicroProfile LRA**: a Jakarta/MicroProfile *specification* (not a DSL) for saga-style long-running actions — participants join an LRA context via annotated REST endpoints; compensation is implicit in the protocol rather than declared as data. A formal comparison study found Axon, Eventuate Tram/ES, and LRA differ mainly in *where* compensation logic lives (event handler vs. protocol callback vs. explicit saga definition). ([LRA integration study](https://is.muni.cz/th/xsq5t/thesis.pdf), [saga comparison](https://jbossts.blogspot.com/2017/12/saga-implementations-comparison.html))
- **Domain Storytelling** (Hofer/Schwentner, tool: **egon.io**): a pictographic notation (actor → activity → work object, in numbered sequence) deliberately **without symbols for conditionals/branches** — it's a requirements-elicitation technique, not an executable DSL; relevant to ElastiCORE only as an upstream discovery tool, not a code-gen input. ([egon.io](https://egon.io/), [domainstorytelling.org](https://domainstorytelling.org/))
- **Eclipse Sirius Web**: a low-code framework for building *your own* graphical/textual DSL editors (Spring+React+GraphQL stack) — could be a future front-end for an ElastiCORE business-logic DSL rather than a competing DSL itself. ([Sirius Web](https://eclipse.dev/sirius/sirius-web.html))

## 6. LLM-Era: Contracting an LLM Step Inside a Deterministic Flow

- **Microsoft Semantic Kernel Process Framework**: targets exactly this niche — "deterministic business workflow orchestration" with event-driven steps built from SK Functions, runs on Dapr/Orleans; a **unified declarative format** for agent/process workflows is on the roadmap (GA targeted ~Q2 2026), explicitly reasoning that "those who know what needs to be done are the best designers" of declarative workflow steps. ([roadmap](https://devblogs.microsoft.com/semantic-kernel/semantic-kernel-roadmap-h1-2025-accelerating-agents-processes-and-integration/))
- **LangGraph**: nodes/edges over a typed shared `State` schema; explicitly supports mixing "deterministic, hand-coded steps with LLM-driven agentic steps in the same graph" — construction can be programmatic (Python) or DSL/JSON-serialized; conceptually an FSM, so it maps cleanly onto the same node/edge vocabulary as BPMN/ASL/Serverless Workflow.
- **Structured outputs as the input/output contract**: OpenAI's Structured Outputs enforces a JSON Schema on the response itself; Anthropic instead routes structured data through **tool use** (define a tool whose input schema is the desired output, force a tool call) — both achieve near-100% schema compliance (~99.7–99.9% reported). This is the practical template for "an LLM step contracts in/out via JSON Schema, just like a `port:` HTTP call." ([comparison](https://tessl.io/blog/anthropic-brings-structured-outputs-to-claude-developer-platform-making-api-responses-more-reliable))
- **Model Context Protocol (MCP)**: open standard (Anthropic, Nov 2024) for connecting LLM apps to external tools/data; current spec **2026-07-28** introduces a stateless protocol core, multi-round-trip requests, cacheable list results, and a formal extensions framework — relevant as the contract shape for an ElastiCORE-generated "AI step" that needs typed tool discovery. ([spec](https://modelcontextprotocol.io/specification/2025-11-25), [2026-07-28 update](https://blog.modelcontextprotocol.io/posts/2026-07-28/))
- **Agent Skills / SKILL.md**: open format (Anthropic, Dec 2025, now on 26+ platforms) — a folder with YAML-frontmatter `SKILL.md` (name+description always loaded; body loaded on match; bundled scripts/references/assets loaded on demand = progressive disclosure). Directly relevant as a *packaging* pattern if ElastiCORE ever wants to generate "skill" bundles alongside services. ([spec repo](https://github.com/anthropics/skills), [DeepWiki spec](https://deepwiki.com/anthropics/skills/6.1-agent-skills-specification))
- **DSPy Signatures**: typed input/output declarations (Pydantic-backed) that express *intent*, not a literal prompt — the framework optimizes the prompt automatically; contrasts with BAML/Guidance/LMQL which constrain a *single call's* output shape but don't optimize task performance.
- **BAML**: a DSL that formalizes LLM calls as **typed behavioral APIs** — explicit input/output schemas, static validation, generates client code across languages; philosophically the closest LLM-era analog to what ElastiCORE does for REST/DB ports (declare a typed contract, generate the call-site code).
- **Guidance / LMQL**: low-level constrained-generation control (grammar/regex-constrained decoding) for a single model call — good for enforcing an output grammar, not for task-level correctness.
- **n8n AI Agent node / Kestra AI tasks**: visual/YAML workflow platforms embedding an LLM-reasoning node that combines system+user prompt+memory into one call and loops over tool calls — the workflow-engine analog of "one `port:`-like step whose implementation happens to be an LLM."
- **GitHub Copilot Workspace / Spec Kit spec-first**: `spec.md` as single source of truth, with `/specify → /plan → /tasks` slash commands generating an executable plan from natural-language requirements — relevant as a *process* pattern (spec drives generation, traceability required) rather than a DSL grammar.

## (i) Expression-Language Comparison

| Language | Java impl | Safety / termination | Typing | Tooling | LLM familiarity |
|---|---|---|---|---|---|
| **CEL** | `cel-java` (official) | Non-Turing-complete, linear-time, no side effects, provably terminating | Static-ish, protobuf/JSON-aware | Growing (k8s, Firebase); formal spec + conformance tests | Moderate — newer, less training data than SQL/JS-likes |
| **FEEL** (DMN) | Built into Drools/Camunda DMN engines | Bounded by DMN engine sandbox; no arbitrary code | Strongly typed against DMN item definitions | Mature decision-table tooling, OMG conformance levels | Low-moderate — niche outside BPM |
| **JSON Logic** | `json-logic-java` (community) | By construction: no `eval`, no loops/gotos/side effects | Untyped (JSON values) | Minimal; community spec, many ports | Low — small footprint but trivially learnable |
| **Rego** | none first-class (OPA runs as sidecar/binary; call via HTTP/WASM) | Turing-incomplete-ish logic language but complex partial evaluation; deep recursion possible | Untyped, unification-based | Very mature (OPA/Gatekeeper/Kyverno-adjacent ecosystem) | Low — steep learning curve widely reported |
| **SpEL** | Native (Spring) | Unsafe by default (`StandardEvaluationContext` = full JVM reflection); must opt into `SimpleEvaluationContext` | Dynamic, Java-typed | Excellent within Spring; IDE support | Moderate — Java-like syntax |
| **JEXL** | Native (Apache Commons) | Sandboxable via permissions API; safer default posture than SpEL | Dynamic | Good, framework-agnostic | Low-moderate |

## (ii) Flow-Representation Comparison

| Representation | YAML-friendliness | Compensation/saga support | Human readability | Code-gen suitability |
|---|---|---|---|---|
| **BPMN 2.0** | Poor (XML-native, not designed for hand-written YAML) | Strong (native compensation events, boundary events) | Good *with* a diagram tool; poor as raw XML | Moderate — mature codegen ecosystem but heavyweight |
| **ASL (Step Functions)** | Good (JSON, YAML supported via SAM/CDK) | Manual (explicit `Catch`/rollback states only) | Good for small graphs, degrades at scale | High — simple typed node schema, easy to emit |
| **CNCF Serverless Workflow** | Excellent (YAML-first, JSON alt) | Strong (built-in try/catch + compensation, saga docs) | Good — designed for "linguistic fluency" | High — unified `task` model, JSON Schema-validated |
| **Statechart (SCXML/XState)** | Good (XState JSON is naturally YAML-portable) | None native (must model compensation as explicit states) | Very good for finite, event-driven logic; poor for linear pipelines | High for state-heavy domains (order/ticket lifecycle), poor for pipelines |
| **Context Mapper flow (CML)** | Good (Xtext textual DSL, YAML-adjacent readability) | None (DDD/architecture focus, not execution) | Very good for architecture-level review | Low for runtime execution, high for scaffolding/contracts |

## (iii) 10 Design Lessons for ElastiCORE's Business-Logic DSL

1. **Pick a restricted, terminating expression language for predicates/guards — CEL is the strongest fit**: Java-embeddable (`cel-java`), non-Turing-complete, linear-time, already battle-tested for exactly this role in Kubernetes CRD validation. Avoid SpEL/JEXL unless sandboxed; avoid Rego unless you also accept its adoption cost.
2. **Every declarative flow representation studied has an explicit, typed escape hatch to code** (BPMN service tasks, ASL Lambda `Resource`, Hasura Actions, Mendix Java actions, Salesforce Apex-from-Flow, BAML's typed client). ElastiCORE's `port:` block is already this shape — extend the same pattern for business-logic steps rather than inventing a new one.
3. **Compensation/saga logic wants to be a first-class DSL construct, not an afterthought** — CNCF Serverless Workflow's try/catch-with-compensation and BPMN's compensation events read far better than ASL's manual `Catch` re-implementation; if ElastiCORE adds multi-step process logic, design compensation syntax up front.
4. **Separate "declare the graph" from "declare the guard"**: every successful system studied composes a flow-shape language (nodes/edges/tasks) with a *different*, narrower expression language for conditions (FEEL, CEL, Rego) — don't try to make one grammar do both.
5. **State machines and linear workflows are different problems** — Symfony Workflow/Sylius and XState both show that entity-lifecycle logic (order status, ticket status) is best modeled as explicit states+transitions+guards, not as a generic workflow graph; ElastiCORE's DDD entities likely want a `state:` block distinct from a `flow:`/`process:` block.
6. **Formal verification is a differentiator, not a luxury** — Cedar's automated-reasoning proofs against its Rust implementation, and CEL's linear-time-termination guarantee, are the concrete evidence base that let adopters trust a DSL in production; even a lightweight "no unbounded loops, no reflection" static check on ElastiCORE's business-logic YAML would put it ahead of ad hoc SpEL usage.
7. **JHipster JDL's restraint is instructive**: a mature, widely-adopted structural DSL sibling to ElastiCORE deliberately stopped at generating a service *stub* and left logic to hand code — validates that ElastiCORE need not (and arguably should not) try to express all business logic declaratively; the win is a well-typed seam.
8. **Context Mapper's tactical-DDD grammar is the closest existing precedent to ElastiCORE's annotation set** — its `.xtext` grammar for Aggregate/Service/Application (use-case flows) is worth mining directly for field/relationship syntax ideas, even though it targets architecture docs rather than runtime code.
9. **For an "LLM-executed step" inside deterministic flow, contract it exactly like a `port:` call**: typed input schema, typed output schema (JSON Schema / tool-use style), explicit model/temperature/timeout config, and a required fallback/error branch — this mirrors both Anthropic tool-use and BAML's "typed behavioral API" framing, and keeps the LLM step orthogonal to (not entangled with) the rest of the deterministic DSL.
10. **DSL longevity correlates with staying declarative-only and delegating execution to a widely-used runtime**, not building a bespoke language+VM: ASL/BPMN/Serverless Workflow/JSON Logic/CEL all lean on existing engines (Step Functions, Zeebe, SonataFlow/kogito, any host language, Kubernetes/Envoy); Dark lang's near-collapse after building both a custom language *and* a custom always-on runtime is the cautionary counter-example — ElastiCORE should keep generating idiomatic Java/Kotlin/TS rather than inventing a business-logic runtime to interpret.

### Recommended Next Step
Fetch the actual `ContextMappingDSL.xtext` grammar and the CEL language-definition (`cel-spec`) EBNF as primary artifacts to model ElastiCORE's new grammar against, and prototype a `logic:`/`rule:` block scoped to CEL-style guard expressions plus a typed `ai:`/LLM-step contract modeled on Anthropic tool-use schemas — both are directly actionable, Java-embeddable, and align with ElastiCORE's existing Spring Boot/JPA code-gen target.
