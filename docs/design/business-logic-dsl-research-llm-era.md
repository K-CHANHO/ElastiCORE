# Research: LLM/AGI-Era Spec-Driven Development — Implications for a Business-Logic DSL

*Research conducted September 2026. Note: many sources below are dated 2025–2026 and postdate my training cutoff (Jan 2026) — treated as live web findings, not verified against prior knowledge. Flagged where uncertain.*

## 1. Spec-Driven Development Movement (2024–2026)

The dominant pattern across vendors: **spec → plan → tasks → generated code**, with the spec as the durable artifact and code treated as increasingly disposable.

- **GitHub Spec Kit** (MIT, released ~Sept 2025): CLI + templates that move work through specification → technical plan → small testable tasks → implementation, agent-agnostic (works with Copilot, Claude Code, Gemini CLI). [github.com/github/spec-kit](https://github.com/github/spec-kit) · [GitHub Blog announcement](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- **AWS Kiro**: three-file spec artifact — `requirements.md` (user stories/acceptance criteria in structured notation), `design.md` (architecture, sequence diagrams), `tasks.md` (dependency-graphed, wave-executed task list). [kiro.dev/docs/specs](https://kiro.dev/docs/specs/)
- **Amazon Q Developer**: also adopted spec-driven workflows and even bridges to Spec Kit via MCP — but note Amazon Q Developer itself has an **end-of-support announcement**, a caution against betting a DSL's roadmap on any single vendor tool. [AWS blog](https://aws.amazon.com/blogs/devops/amazon-q-developer-end-of-support-announcement/) · [cremich.cloud](https://cremich.cloud/specification-driven-development-with-amazon-q-developer)
- **Sean Grove (OpenAI), "The New Code"** (AI Engineer conf, ~2025 — exact date uncertain): thesis that specs, not code, are the durable source artifact; code is "a lossy projection from the specification." Provocatively: current practice inverts this — we carefully version-control the binary (code) and discard the source (prompt/spec). [transcript](https://lawwu.github.io/transcripts/8rABwKRsec4.html)
- **Martin Fowler + Unmesh Joshi, "DSLs Enable Reliable Use of LLMs"** (martinfowler.com, **July 14, 2026** — directly on-topic for ElastiCORE): DSLs work because they (a) narrow the solution space so few-shot examples generalize, and (b) ship with a **deterministic validator** (parser/schema/type-checker/compiler) enabling closed-loop self-correction. Upfront specification is "a hypothesis to be revised, never a finished blueprint" — but the **DSL itself, not the prompt, is the enduring artifact**. LLMs play two roles: brainstorming partner during DSL/abstraction design, then NL-interface once the DSL is established. [martinfowler.com/articles/llm-and-dsls.html](https://martinfowler.com/articles/llm-and-dsls.html)
- **OpenAI Codex `AGENTS.md`**: started as a cross-vendor convention (Codex, Amp, Jules, Cursor, Factory), now stewarded by the **Agentic AI Foundation** (Linux Foundation). Plain markdown, no required schema, but recommended sections (overview, build/test, style, security, commit rules); layered global → repo → subdirectory scoping. Read by 30+ agents. [openai/codex docs](https://github.com/openai/codex/blob/main/docs/agents_md.md)
- **Tessl**: positions itself as "spec-as-source" — code stays permanently disposable. Framework (closed beta) + **Spec Registry** (open beta, 10,000+ specs) describing external library behavior/intent to prevent API hallucination, plugged into agents via MCP. [tessl.io](https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry) · [docs.tessl.io](https://docs.tessl.io/introduction-to-tessl/concepts)
- **Cursor**: `.cursor/rules/*.mdc` (glob-scoped, four activation modes) plus **Plan Mode**, which researches the codebase and produces a markdown plan with file/code references before any edit. [cursor.com/docs/rules](https://cursor.com/docs/rules) · [Plan Mode blog](https://cursor.com/blog/plan-mode)

**What's machine-checkable**: task decomposition/dependency graphs (Kiro waves), schema/grammar conformance, acceptance-criteria-as-tests. **What stays NL/human-judged**: intent, "why," architectural trade-offs, UX taste.

**What this means for ElastiCORE**: the industry consensus already matches ElastiCORE's bet — the YAML DSL *is* the spec-kit "spec" layer, generate-once files are the "tasks" layer. The gap: competitors' specs are mostly prose-with-structure; ElastiCORE's is a real grammar with a compiler, which per Fowler/Joshi is the more defensible position — but ElastiCORE currently lacks the declarative *business-logic* layer (invariants/behavior) that these tools leave entirely to freeform code/NL.

## 2. Verifiable-Generation Research

Evidence that a formal/declarative layer measurably improves LLM correctness:

- **Clover (2023)**: checks *consistency* between code, docstrings, and formal (Dafny) annotations rather than absolute correctness. On CloverBench (60 hand-crafted Dafny examples): **87% acceptance of correct code, 100% rejection of incorrect code**; on MBPP-DFY-50, 89% correct-accept with 6/6 incorrect samples caught. [arxiv.org/abs/2310.17807](https://arxiv.org/abs/2310.17807)
- **Vericoding Benchmark (2025, POPL 2026)**: largest benchmark to date (12,504 tasks). LLM success rates on formally-verified synthesis: **Dafny 82.2%, Verus 44.2%, Lean 26.8%** — the gap tracks how much of the verification burden falls on the LLM vs. the checker (Verus requires ghost/native type reasoning and overflow proofs). Separately, **DafnyBench pure-verification (proof-only) success rose from 68% to 96% within one year**, showing verification-in-the-loop improves fast even where generation lags. [arxiv.org/pdf/2509.22908](https://arxiv.org/pdf/2509.22908)
- **AlphaVerus**: bootstraps formally verified code generation via self-improving translation + "treefinement" (tree search + proof repair). [CMU PDF](http://www.contrib.andrew.cmu.edu/~bparno/papers/alpha-verus.pdf)
- **Baldur (FSE 2023)**: whole-proof generation and *repair* — feeds the prior candidate proof + compiler error back into a repair model, a pattern directly reusable for "regenerate ElastiCORE-declared invariant, fail, repair" loops. [arxiv.org/pdf/2303.04910](https://arxiv.org/pdf/2303.04910)
- **Property-based testing as oracle**: PBT lets LLMs assert *invariants* rather than input/output pairs, giving stronger oracles — but current LLM-generated properties are "frequently trivial or incorrect," so PBT augments rather than replaces human-declared invariants. [arxiv.org/html/2506.18315v1](https://arxiv.org/html/2506.18315v1)
- **TiCoder (test-driven interactive generation)**: guided test-based intent clarification produced a **45.73% absolute improvement in pass@1** over 5 interaction turns (MBPP/HumanEval), enough to bring small models to GPT-4-32k-class accuracy. [arxiv.org/pdf/2208.05950](https://arxiv.org/pdf/2208.05950)
- General finding across specification-driven-generation studies: "adding any type of structured specification significantly improves output quality" vs. NL-only baselines (specific % not consistently reported across studies — **flagged as directionally strong but not a single clean number**).

**What this means for the DSL**: the accuracy gains from Clover/Vericoding/TiCoder all come from the *same mechanism* Fowler describes — a machine-checkable artifact + closed feedback loop. ElastiCORE's proposed `@invariant`/`@specification` annotations, if compiled to runtime assertions or generated tests, become exactly this oracle. Full Dafny/Lean-style formal proof is likely overkill for business CRUD logic — the evidence favors **property/contract-level checking** (Design-by-Contract style, Meyer's territory — see §5) over full formal verification for this domain.

## 3. Grammar-Constrained Generation & DSL Syntax Accuracy

- **Grammar-constrained decoding** (XGrammar, llguidance, Outlines) compiles a JSON Schema/BNF grammar into an FSM that masks invalid tokens at each decode step — **near-zero runtime overhead** (llguidance ≈50μs/token for a 128k-vocab tokenizer), now standard in vLLM/SGLang. [XGrammar](https://blog.mlc.ai/2024/11/22/achieving-efficient-flexible-portable-structured-generation-with-xgrammar) · [llguidance](https://github.com/guidance-ai/llguidance)
- **Grammar Prompting (Wang et al., NeurIPS 2023)**: for DSL generation, don't just show examples — show each demonstration annotated with the *minimal BNF subset* needed to produce it; at inference the model first predicts a grammar, then generates conforming output. Demonstrated gains in semantic parsing, PDDL planning, SMILES molecule generation. [arxiv.org/abs/2305.19234](https://arxiv.org/abs/2305.19234)
- **YAML vs. JSON**: JSON generally outperforms YAML on syntax/structure accuracy in controlled studies (e.g., 0.986 syntax accuracy for Mistral-Small on JSON-to-JSON), while forcing structured output can degrade reasoning quality by ~10–15% in some benchmarks — a real trade-off between reliability and reasoning depth. [arxiv.org/html/2501.10868v1](https://arxiv.org/html/2501.10868v1) · [DSL fine-tuning vs RAG study](https://arxiv.org/html/2407.02742v1)
- **Custom DSL hallucination**: LLMs specifically struggle with **unfamiliar custom function/annotation names**, with hallucination and syntax-error rates rising as the DSL's custom vocabulary grows — directly relevant to ElastiCORE's `@invariant/@event/@factory/@specification` annotations, which are bespoke and won't be in any model's training data. [CallNavi](https://arxiv.org/pdf/2501.05255)
- **Mitigations** converge on the same three levers: (1) docs-in-context/few-shot grammar excerpts (Grammar Prompting), (2) JSON-Schema/grammar-constrained decoding at generation time, (3) compile-and-repair loops so a syntactically-invalid annotation fails fast and is corrected — the same closed-loop pattern as §2.

**What this means for the DSL**: keep the YAML surface (human-readable, matches existing ElastiCORE convention) but (a) ship a **formal grammar/JSON Schema for the new business-logic annotations** so IDE/agent tooling can grammar-constrain generation, (b) put a **compact BNF or annotated few-shot cheat-sheet in the guide docs** (already partially done via `elasticore-annotation-guide.md`) specifically because generic LLM pretraining has zero exposure to `@invariant`/`@specification`, and (c) treat every DSL validation failure as free training signal for a repair loop, not just a build error.

## 4. Agent Interoperability Standards

What a "business capability" must declare to be usable by agent infrastructure, per current specs:

- **MCP (Model Context Protocol)**: three primitives — **tools** (name + JSON-Schema input/output, invoked actions), **resources** (URI-identified, read-only context, annotated with audience/priority/last-modified), **prompts** (reusable instruction templates). No native side-effect or auth metadata field in the core primitive schema itself — that's left to transport/host. [modelcontextprotocol.io spec](https://modelcontextprotocol.io/specification/2025-06-18/server/prompts)
- **Anthropic Agent Skills**: a folder with `SKILL.md` — YAML frontmatter requires only **name + description** (description doubles as the routing signal); optional fields include version, tags, author, spec_version. Progressive disclosure: name/description loaded always, full body loaded on match, scripts/assets loaded on demand. [github.com/anthropics/skills](https://github.com/anthropics/skills) · [agentskills/agentskills spec](https://github.com/agentskills/agentskills)
- **Google A2A (Agent2Agent)**: **Agent Card** — JSON metadata at `/.well-known/agent.json` declaring identity, skills (with input/output *modes*, not full schemas), service endpoint, and **auth schemes** (OAuth2, API key, OIDC, bearer). This is the standard with the most explicit **auth** metadata of the group. [a2a-protocol.org/latest/specification](https://a2a-protocol.org/latest/specification/)
- **OpenAI function calling**: name + JSON-Schema parameters + description — no side-effect or auth field, by design left to the calling application.
- **Semantic Kernel / LangGraph**: no standardized capability-metadata schema; SK wraps prompts as "semantic functions" alongside native code (enterprise/.NET-oriented), LangGraph models workflows as typed graph nodes/edges with app-defined state — both are *execution* frameworks, not capability-description standards.
- **Apache Ossie (incubating, Linux Foundation/Apache)** — genuinely exists, worth flagging as low-familiarity: a semantic-model interchange spec where every entity/field/metric carries an **`ai_context`** attribute so agents get business intent alongside technical schema, in a shared YAML/JSON format portable across BI/AI tools. [ossie.apache.org](https://ossie.apache.org/) · [apache/ossie docs](https://github.com/apache/ossie/blob/main/docs/index.md)

**Common required metadata across all of these**: `name`, `description` (for routing/discovery). **Inconsistently present**: input/output schema (MCP tools yes, A2A skills only "modes"), auth (A2A explicit, MCP/OpenAI absent from the primitive itself), and **side-effects are declared nowhere as a first-class field in any of these standards** — it's exactly the gap §6's capability/policy layer (Cedar/OPA, WIT capabilities) is trying to fill separately.

**What this means for the DSL**: an ElastiCORE-generated business capability (e.g., a `@specification`-declared use case) should be able to emit, almost for free, an MCP tool descriptor (name/description/JSON-Schema I-O from the DTO/port definitions already in the DSL) and an A2A-style skill card — but ElastiCORE should *own* the side-effect/auth declaration itself (nothing upstream standardizes it yet), likely alongside the Cedar/OPA-style policy layer in §6.

## 5. AGI-Era Forward Positions

- **DORA 2026**: as AI accelerates generation, the bottleneck shifts to **specification and verification** — "specifications are no longer overhead relative to implementation but the scarce resource." Identifies a **"verification tax"**: review time is *increasing* even as total lead time falls, because reviewers face more code they didn't write. 30% of developers (per the 2025 DORA report) report little/no trust in AI-generated code. [dora.dev/insights/balancing-ai-tensions](https://dora.dev/insights/balancing-ai-tensions/)
- **Bertrand Meyer**, *"AI for Software Engineering: From Probable to Provable"* (CACM, ~Aug–Oct 2025): argues for combining generative AI's creativity with **formal specification and Design-by-Contract-style verification** — Meyer's long-standing thesis (contracts as executable specs) now explicitly reframed for the LLM era. [arxiv.org/pdf/2511.23159](https://arxiv.org/pdf/2511.23159)
- **Leslie Lamport**: TLA+ remains the reference point for "programmers need abstractions" — his position (pre-dating the LLM wave but widely re-cited in this literature) is that precise, checkable specification-writing is a *distinct skill* from coding and the one that scales. [thenewstack.io interview](https://thenewstack.io/tla-creator-leslie-lamport-programmers-need-abstractions/)
- **Simon Willison**: distinguishes *vibe coding* (unreviewed LLM output) from responsible AI-assisted development; his rule — never commit code he "couldn't explain... to somebody else" — implies the reviewability of the artifact, not who wrote it, is what matters, which is an argument *for* a declarative spec (easier to review than generated code) over raw code review. [simonw.substack.com](https://simonw.substack.com/p/not-all-ai-assisted-programming-is)
- **Andrej Karpathy**: "the hottest new programming language is English" (Feb 2023); coined "vibe coding" (Feb 2025); by 2026 commentary describes "agentic engineering" superseding vibe coding as the professional default — i.e., the industry's own arc moved *away* from pure-NL coding toward structured agent workflows, echoing the spec-driven trend in §1. [x.com/karpathy/status/1617979122625712128](https://x.com/karpathy/status/1617979122625712128)
- **Gergely Orosz**: AI-generated code is often "subtly wrong" — compiles, passes a glance, but has logic/architecture errors that require senior-engineer effort to catch, sometimes offsetting the productivity gain entirely; recommends tests as the de-risking mechanism. [Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/beyond-vibe-coding-with-addy-osmani)
- **"AGI's Last Bottlenecks"** essay and related arxiv work on **"Constitutional Spec-Driven Development"** (2026, arxiv 2602.02584) explore enforcing security/correctness-by-construction directly from the spec layer, and empirical study designs for spec-driven LLM code gen are now an active research subfield (arxiv 2601.03878, 2603.25773 "The Specification as Quality Gate"). [ai-frontiers.org](https://ai-frontiers.org/articles/agis-last-bottlenecks) · [Constitutional SDD](https://arxiv.org/pdf/2602.02584)

**On maintainability specifically**: no single controlled study directly A/B-tests "review a declarative spec" vs. "review generated code" at scale — but the DORA verification-tax finding, Orosz's "subtly wrong" observation, and Willison's explainability rule all converge on the same implication: **a shorter, declarative, checkable artifact is cheaper to review than the code it expands to**, because the reviewer verifies intent once rather than re-deriving intent from implementation every time. *(This synthesis is my inference from convergent evidence, not a single cited study — flagged as such.)*

## 6. Safety / Governance

- **Cedar** (AWS): authorization language with *formally verified semantics*, designed for per-request policy decisions at scale. **OPA/Rego**: CNCF-graduated, the incumbent standard for admission-time policy-as-code in cloud/K8s. Both are now being repurposed as **agent guardrail layers** — e.g., Microsoft's **Agent Governance Toolkit** (open-sourced ~April 2026) runs a single policy evaluator against YAML rules, Rego, and Cedar together, intercepting every agent action pre-execution at sub-millisecond latency. [Microsoft OSS blog](https://opensource.microsoft.com/blog/2026/04/02/introducing-the-agent-governance-toolkit-open-source-runtime-security-for-ai-agents/) · [OPA/Rego/Cedar tutorial](https://microsoft.github.io/agent-governance-toolkit/tutorials/08-opa-rego-cedar-policies/)
- **Capability-based / sandboxed-effects declarations**: emerging pattern where a tool/skill's required capabilities are declared in a machine-readable manifest (e.g., WIT for Wasm modules) so policy engines can flag mismatches ("claims calculator, imports network") automatically before deployment — directly analogous to what a `@specification`'s declared side-effects should enable. [arxiv 2604.11839](https://arxiv.org/html/2604.11839) · [Lingering Authority: revocable resource/effect capabilities for coding agents](https://arxiv.org/pdf/2606.22504)
- **EU AI Act**: Article 12 sets a **6-month minimum retention** for high-risk-system logs; Article 18 requires logs stay accessible for **10 years after withdrawal**. A defensible audit-trail baseline (per industry guidance, not the Act's literal text) includes ~12 fields per AI-influenced decision: timestamp, decision ID, human identity, AI system+version, model+version, inputs with provenance, **the specific policy/rule invoked**, human-readable reasoning, output, downstream action, human review status, tamper-evident proof. Guidance explicitly recommends capturing **template ID + version, not raw prompt text**, for exactly this kind of auditability. [Kognitos 2026 checklist](https://www.kognitos.com/blog/ai-audit-trail-requirements-2026-checklist/)

**What this means for the DSL**: a versioned, declarative spec is *structurally* what EU AI Act Article 12/18 wants captured (a stable "policy/rule invoked" reference beats raw generated code or raw prompts as an audit artifact) — and it's exactly what Cedar/OPA-style engines expect as their policy input. ElastiCORE's generate-once boundary is a natural hook for a **declared side-effect/capability manifest** per service method, checkable by an external policy engine before the LLM-filled portion executes.

## 10 Design Principles for a Business-Logic DSL in the LLM/AGI Era

1. **The DSL, not the prompt or the generated code, is the source of truth.** Prompts are disposable; the spec is versioned, reviewed, and diffed. *(Fowler/Joshi, martinfowler.com; Sean Grove, "The New Code")*
2. **Every declared construct needs a deterministic validator, not just a schema.** Parseability isn't enough — pair each new annotation (`@invariant`, `@specification`) with a compiler/type-checker that can reject and explain, enabling closed-loop repair. *(Fowler/Joshi; Baldur; Clover)*
3. **Prefer contract-level (Design-by-Contract) checking over full formal proof for business logic.** Full Dafny/Verus/Lean-grade verification is expensive and its accuracy on hard targets (Verus 44%, Lean 27%) isn't there yet for arbitrary business rules — pre/postconditions and invariants get most of the reliability benefit at a fraction of the cost. *(Bertrand Meyer, CACM 2025; Vericoding Benchmark 2025)*
4. **Treat unfamiliar DSL vocabulary as a hallucination risk to be actively mitigated, not assumed away.** Custom annotations like `@invariant`/`@factory` have zero pretraining exposure — ship grammar excerpts / few-shot exemplars in-context (skills, guide docs) and grammar-constrain generation at decode time. *(Grammar Prompting, Wang et al. 2023; CallNavi custom-DSL hallucination findings)*
5. **Keep YAML for human authorship, but expose a formal grammar/JSON Schema for machine authorship.** Structured decoding needs the schema even where humans prefer YAML's readability; don't force one syntax to serve both audiences equally well. *(XGrammar/llguidance; JSON-vs-YAML accuracy studies)*
6. **Make the spec cheaper to review than the code it expands to — that's the entire point.** The reviewer should verify intent once in the DSL, not re-derive intent from generated Kotlin/TS on every change. *(DORA 2026 "verification tax"; Orosz "subtly wrong" code; Willison's explainability rule)*
7. **Declare side-effects and required capabilities as first-class DSL fields — no upstream standard does this yet.** MCP/OpenAI/A2A specify name+schema (and A2A specifies auth) but none formalize side-effects; this is exactly the empty seat ElastiCORE can fill for its own generated capabilities. *(MCP spec; A2A Agent Card spec; capability-manifest / WIT literature)*
8. **Generate agent-interoperability descriptors from the DSL, don't hand-write them.** A `@specification`-declared use case should mechanically produce an MCP tool descriptor and/or A2A skill card from the same DTO/port definitions already in the model, keeping the DSL as the single source. *(MCP, A2A, Anthropic Agent Skills metadata requirements)*
9. **Version and reference the spec, not the prompt or the raw generated diff, as the audit artifact.** Regulatory guidance already prefers "template ID + version" over prompt text for traceability — a versioned business-logic DSL entry is a stronger compliance artifact than either. *(EU AI Act Art. 12/18; audit-trail baseline guidance)*
10. **Route side-effecting generated code through an external declarative policy layer (Cedar/OPA-style), keyed off what the DSL declares.** Don't rely on the LLM to self-limit; let a policy engine check the DSL's declared capabilities/invariants against runtime requests before the LLM-filled implementation executes. *(Cedar; OPA/Rego; Microsoft Agent Governance Toolkit)*
