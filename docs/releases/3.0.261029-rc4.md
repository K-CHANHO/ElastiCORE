The fourth release candidate of 3.0.

### Bug fixes

- **The v3 CoreService fetches `@fetchjoin` relations.** This covers the plugin's default, hexagonal, DDD and Kotlin.
  - As in 2.x, a relation marked `@fetchjoin`, or every relation to an entity under `table.autoJoin`, is fetched with the root in the paged search (`findBySearch`). The fetch is a LEFT JOIN FETCH that leaves out the count query.
  - `withJoinFetches()` is generated for such an entity, so an extension service calling it compiles again.
  - Before, each listed row loaded the relation with a query of its own (N+1). Paging five orders of five customers made five extra customer selects; now it makes none.
- **A domain whose mode is not `jpa` is refused, not written as JPA.**
  - The rule engine did not read `config.mode`, so a `mode: mongo` domain got JPA entities, repositories and services without a word.
  - `elcore3` now stops before writing any source and points to the 2.x generator: `elasticore { output = 'v2' }`, or `./gradlew elcore`.
  - `uml` and `dsl` beside `jpa` get a warning.
- **2.x-compatible controller:** given a declared `@searchable` DTO, the search endpoint takes it, as 2.x does and as the service already did.

### Compatibility checks

- The 2.x reference model now declares what it did not before, so the checks compare these too:
  - `@schema`, a class-level `@jpa:Where`, `@pattern`, `@size`, `@notnull`, a field `@readonly`;
  - required and optional relations in a declared search DTO;
  - `@searchBypass`.
- Results: `elcoreRulesCheck -Pstrict` reports 157 MATCH / 0 DIFF / 2 ACCEPTED, and `elcoreTreeCheck` compares 238 files with 0 differ / 0 missing / 0 extra.

### Documentation

- The migration guide lists what moving 2.x's code to v3 changes. Examples are constructors that take the key, imports used inside protected blocks, and how `save`, `update`, `delete` and `updateBySpecification` behave.
- The dev guide says how protected blocks move on regeneration, and where `withJoinFetches()` is generated.
- The annotation guide has the entity-level `@readonly` and `@restExclude`.

### For contributors

- A pull request records its change as a file of its own in `changes/` (see `changes/README.md`). It no longer edits the history directly; the release assembles the fragments into it.
- The samples no longer commit copies of the guides.
- A CI job, **Change record**, checks this on every pull request and says what to do when it fails.
- GitHub releases carry English notes.
