The third release candidate of 3.0.

**The Gradle plugin generates the 3.0 code by default.** A layered Java project that declares nothing now gets the `jpa-springboot-v3` bundle. A project that keeps the code 2.x generates says so with `elasticore { output = 'v2' }`. A project that holds code 2.x generated and chose neither is stopped before any source is rewritten, with that choice to make. The 2.x generator's output and the `jpa-springboot` bundle are unchanged.

### Changes

- **The 3.0 code by default; 2.x's code is `output = 'v2'`.**
  - With no declaration, or with `architecture = 'layered'`, the build runs `elcore3` on `jpa-springboot-v3`.
  - `output = 'v2'` runs the 2.x generator, and `elcore3` run by hand writes the 2.x-compatible code. `-Pv2` and `-Pv3` decide a single run.
  - A domain whose `env.yml` names `jpa-springboot` keeps 2.x's code.
  - Refused: `output = 'v2'` together with a hexagon, a domain model, Kotlin, the project's own rule sets or a v3-only rule in `env.yml`; also `-Pv2` and `-Pv3` together.
  - **Not silently rewritten:** a project that chose nothing is stopped and no source is written when either is true:
    - its sources carry the hash line of a 1.x or 2.x generator;
    - its last `elcore3` run was 2.x-compatible (`build/elasticore/server.mode`).
  - The initialization wizard writes `jpa-springboot-v3` for layered Java and tells the project to run `elcore3`.
  - [Migration guide](https://github.com/xsko/ElastiCORE/blob/main/elasticore-project/elasticore-base/src/main/resources/elasticore-guide/elasticore-migration-guide.md) (Korean).
- **Ossie export: a portable expression is the top-level `sql`.** This follows [apache/ossie#617](https://github.com/apache/ossie/pull/617).
  - Column names, portable `@formula` expressions and metrics are written as `expression: { sql: "..." }`.
  - A subquery `@formula` stays a single `ANSI_SQL` dialect entry.
  - The expression text is unchanged.

### Bug fixes

Found by generating a 9-domain project with `-Pv3` and comparing it with 2.x:

- **v3 and Kotlin entities keep the class annotations the DSL gives them** (`@jpa:Where(...)`, `@jpa:Inheritance(...)`, env.yml `@entity:` mappings). They were dropped without a warning, so a soft-delete filter disappeared.
- **A declared search DTO keeps a required relation**, as 2.x does. The condition for a relation marked `!` used to be lost. It stays optional in the search: no `@NotNull`.
- **AI tool descriptions name the entity with its label** (`Accident (accident)`), as 2.x does.
- **A TypeScript search DTO declares a relation by its entity's key** (`insurer?: { id: string }`). It used to import an entity module that is never written, which stopped `tsc` with TS2307.

### Build

- CI compiles the generated TypeScript: the Kotlin sample's model, and the pet store's client with its pages.
- CI fails when the build leaves any sample's `blueprint/` files different from what is committed: the guides, their index and the Ossie model.
